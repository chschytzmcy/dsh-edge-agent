0. 先认清两件事

不看懂这两件事,后面的"waterfall vs emit"就是糊涂账

⛔ waterfall 钩子(打饭阿姨 · 能改菜)
dsh 把所有 listener 包成洋葱:你可以不调 next() = 自己拍板改菜(拦截)、调 next() = 让后面的人先看再决定(拿默认)、throw = 自己炸了 → 整个洋葱都炸(短路退出)。能改写主流程的结果。
🔵 emit 钩子(记账员 · 4 类活儿)
dsh 把所有 listener 当 observer(记账员)并发触发。不能改主流程(return 值被丢弃,throw了也只是 logger.warn 一下)。但可以做 4 类活儿:①记日志(诊断)、②重建内部缓存(打 tag)、③改自己私有状态(如 setRealm)、④推给外部消费者(SSE chunk 写 socket)。 
// ⛔ waterfall 钩子 = 你就是打饭阿姨
on('agent/pre-step', async (payload, next) => {
  if (isAttack(payload)) throw new Error('attack-detected')  // ③ 自己炸了,整条洋葱短路
  const decision = await next()                                // ② 让后面的人看
  decision.messages = sanitize(decision.messages)                       // ① 改菜再往下传
  return decision                                                  // 或 return { kind: 'reject', reason } = 把菜扔了
})

// 🔵 emit 钩子 = 你只是记账员
on('tools/result', (exec, result) => {
  this.ctx.logger?.info?.(`[audit] ${exec.name} done`)   // 记一笔,return 值被丢弃,throw 只 logger.warn
})

// 🔵 emit 钩子的"写 socket 转发"用法 = http-api 在 session/event
// 同一个 on() 注册的 listener 体里,按 event.type 分支处理:看到 chunk → 写 socket;看到 done → 关连接。
// "改"的是 HTTP socket,不是 dsh 主流程(emit 模式 return 值被丢弃)。
on('session/event', (session, event) => {
  if (event.type === 'assistant/chunk') res.write(event.data.chunk)
  if (event.type === 'assistant/message') { res.write('event: done\n\n'); res.end() }
  if (event.type === 'turn/end' && event.data._edgeReject) res.writeHead(403, ...)
})
生活类比
waterfall = 打饭窗口阿姨(能改菜、拒菜、报错);
emit = 旁边记账员(只能看、看完了记一笔、记错没事)。
同步异步不是关键 —— 阿姨可以慢悠悠想(async await)再决定,也可以一看就拍板(sync)。关键是能不能改菜。

1. 纵向流程 — 请求从进入到流出,流过哪些挂载点

每行 = 一个挂载点。📍 做了什么(在这钩子上做什么)、→ 对后面的影响(下游链路被它改成了什么)。按请求流经顺序排列。冷启动 ⑧ 不在请求链上,放最末。

t = 0
HTTP
① HTTP POST :21017 路由层
Node http.createServer + 自研路由表 — 不属于 dsh event 系统(dsh 看不见)。这是 dsh-edge-agent 唯一对外门面。
http-api
📍 做了什么:createServer() 监听 :21017 → 匹配路由(/v1/chat / /v1/chat/stream / /v1/health 等) → 解析 body → 写 access log → 调 Session.chat() 注入 dsh-agent-loop → 同时挂 session/event listener 准备回流。
→ 对后面的影响:HTTP body 被拆成 { sessionId, message, agent, stream } 四元组,从这一刻进入 dsh event 系统,触发 ②③④⑤⑥⑦ 整条链路。client 关 socket → session.abort() 立刻停后续所有阶段。
t = T₁
pre-step
② agent/pre-step waterfall × 2
dsh-agent-loop 每一步开始前。waterfall → 可改 messages、可 reject、可 throw 短路。整个 dsh-edge-agent "拦"主要发生在这层 + ②.⑤ Layer 1.5 + ⑤ Layer 3(Layer 1 + 隐私 4 步管线在这层)。
input-guard (隐私 4 步管线) waterfall
📍 做了什么(4 步串行,每步 await 前一步):
① await promptGuard.checkInput(text) → 60+ 条正则攻击检测。不 safe → REJECT 短路(L766-771 早返),不再跑 ②③④;
② privacyPolicy.matchRouting(text) → 同步(不调 LLM),纯遍历 privacy-policy.json 里 10 条 routingRules,逐条 RegExp.test(text),第一条命中就 return(顺序敏感)。返回 {realm, confidence, rationale}(7 LOCAL / 2 REJECT / 1 CLOUD,confidence 0.7-0.95)。REJECT → 早返(L818-823);
③ await intentRouter.classify(text) → 仅在 ② 没命中 / confidence<0.7 时才跑(§7.87.13.2 修复后)。若 ② 命中 + confidence≥0.7 + 非 REJECT,直接用 ② 的 realm 作权威 category,③ 完全跳过(省一次 local-llm 调用,且不让 LLM 覆盖 PII 规则 — 防"身份证号 + 查天气"被 LLM 判 CLOUD 漏 PII);
④ await sanitizer.sanitize(text, sessionId) → 仅在 category=CLOUD 时才跑,PII → <PHONE:abc> 占位符,LOCAL/SANITIZED 不脱敏。sanitize 失败 → ③ 阶段降级 LOCAL(PII 不出端)。
子流程: ① promptGuard.checkInput → ② privacyPolicy.matchRouting → ③ intentRouter.classify → ④ sanitizer.sanitize ↑ ① unsafe / ② REJECT 即 return,后续跳过
→ 对后面的影响:① 消息改写后的 decision.messages(含占位符)进入 ④⑤,LLM 永远看不到明文 PII;② 短路attack/REJECT → throw → dsh-agent-loop 翻译 {kind:'blocked'} → 后续阶段全跳过;③ 路由category 由 ③ 阶段读,改 provider: cloud-llm → local-llm(sanitize 失败兜底)。🚫 REJECT 时在 throw 前调 attachRejection(agent, {kind, reason, riskLevel}) 把 _edgeRejection 写到 agent 对象 — 因为 dsh-agent-loop:539 会丢 reason 字符串,这张小抄是给 ⑦ http-api 看的。
realm-skill-bridge (Layer 1) waterfall
📍 做了什么:从 decision.messages 里删掉 agent realm 不允许的 <available_skills> 条目(例:agent realm=LOCAL → 删 CLOUD-only skill)→ return 改写后的 decision。
→ 对后面的影响:④ llm/stream 拿到的 messages 里 LLM 只看到被授权的 skill 列表 → LLM 不会去调不该调的工具 → Layer 1 是"目录级"防御。真要 LLM 想调越界工具,还要靠 ②.⑤ Layer 1.5 过滤 tool schema + ⑤ tools/pre-execute Layer 3 兜底拒执行。

stream
④ llm/stream waterfall × 1
LLM 流式响应。waterfall → 可包 AsyncGenerator、可对每个 token 反脱敏。坑点:async function 包 AsyncGenerator 会破坏 stream 协议(§7.38 bug,Promise<AsyncGenerator> → for-await 炸)。
input-guard (反脱敏) waterfall
📍 做了什么:对每个 text-delta chunk 调 sanitizer.desanitize(chunk, sessionId)(用 ② 阶段写的同一份 sessionId 映射表)→ 占位符还原成明文 PII → return 包装后的 AsyncGenerator(外层 yield)。
子流程: drain stream chunks → 对每个 text-delta → desanitize 占位符 → yield 明文 chunk ↑ listener 是 sync 不是 async(防 §7.38)
TTL 机制: 每次 desanitize 刷 lastAccess → 静默 15min → sweep 清 map → mapping 找不到 → return 原文 ↑ 占位符字面量留 chunk,链路不挂
→ 对后面的影响:① SSE 明文⑦ session/event 阶段 http-api 拿到的是已反脱敏的明文 chunk,SSE 直接透传给客户端(浏览器/前端看到原文 PII);② 触发工具收尾助手消息含 tool_calls → dsh-agent-loop 触发 ⑤ tools/pre-execute;③ TTL 兜底sessionTtlMs=900_000(15 min,对齐 confidential 档)。sessionMappings 内存直接持明文 PII → 三层生命周期:① 主动http-api.dropSessionBuffer → purge;② sweepsweepExpired 每 60s 扫过期 map,清掉明文,unref() 不钉进程;③ LRUmaxSessions=1000 超限淘汰。过期行为:desanitizeSync 查 sessionMappings.get(sessionId) → undefined → return text(不 throw);映射在场但单 token 查不到 → mapping.placeholders.get(whole) ?? whole,那项留字面量,其他照常还原。续命:lastAccess = Date.now() 每次反脱敏刷新,活跃聊天永不过期。

dsh-tools 真要调用工具前。waterfall → 可 return {kind:'reject', reason} 不调 next() 让工具不执行,可 throw 短路。数据安全分级"真正拦不拦"的权威 gate(Layer 1 + 1.5 是目录/schema 级,这层是执行级)。
realm-skill-bridge (Layer 3 权威 gate) waterfall
📍 做了什么:读 exec.toolName 的 realm tag(⑧ 冷启动时打的)→ 读 session/agent 的 realm 配置 → 比对:agent.realm ⊇ tool.realm 才放行;否则 return {kind:'reject', reason:'realm-blocked'} 不调 next()。
子流程: 读 toolName realm tag → 读 agent.realm → agent ⊇ tool? → return reject ↑ 否 → return {kind:'reject'} 不调 next()
→ 对后面的影响:① 拒 → LLM 重试工具被拒 → LLM 收到 reject reason 当 tool result → 进入下一轮 LLM call(④ 再来一次);② 留痕拒收事件落 audit.security(realm violation);③ 放行真要执行 → ⑥ tools/result 阶段回写结果。跟 Layer 1 / 1.5 互补:Layer 1 防 LLM 看到 skill 目录,Layer 1.5 防 LLM 看到 tool schema,Layer 3 防 LLM 调工具 — 三层一起拦才稳。说明:此处不再挂 PII 监测 / 滑动窗口限速 — CLOUD realm 本就出去,DSSH 上游 tools.guard() + maxParallelToolCalls=10 + AbortController + MAX_TURNS_EXCEEDED 已覆盖大多数情况(详见 §7.92.1)。

🌐 整体效果

请求流向:客户端 POST :21017/v1/chat/stream → ① http-api 拆 4 元组 → ② input-guard 隐私 4 步管线 + realm Layer 1 目录过滤 → ②.⑤ realm Layer 1.5 tool schema 过滤(assemble)→ ③ input-guard provider 改写 → ④ LLM 流式调用 + 反脱敏 → ⑤ realm Layer 3 拒执行 → ⑥ audit/ops 落盘 → ⑦ http-api SSE 回流 + REJECT 标签读 → 浏览器收到 token。

  • 3 道防御纵深:② Layer 1 目录过滤(skills)→ ②.⑤ Layer 1.5 schema 过滤(tools)→ ⑤ Layer 3 执行拦截(realm tag)。任何一道独立可挡。
  • 3 道 PII 保护:② sanitize 明文 → 占位符(LLM 看不到)→ ③ sanitize 失败 cloud→local(PII 不出端)→ ④ desanitize 反脱敏(给客户端还原)。
  • 3 类观测:audit.jsonl(行为审计,所有阶段共写) / ops.jsonl(耗时/状态,⑥ + ⑦)/ file-logger(运行时日志,所有阶段共写)。
  • 1 条 REJECT 标签流:② input-guard throw 前贴 _edgeRejection → dsh-agent-loop 翻译丢 reason → ⑦ http-api 读标签转 4xx(reason 靠小抄跨过翻译断层)。
  • 4 个路由决策:② 分类(sanitize)→ ③ 切 provider(sanitize 失败)→ ⑤ 限速(超 N 次)→ ⑦ 转 HTTP 状态码(REJECT)。每一刀都改请求的物理路径。

冷启动自检(不在请求链上,启动时跑一次)

这一组 listener 不响应任何单次请求,只在冷启动时 dsh-tools / dsh-skills register 完毕时被 emit 触发。本项目的 realm-tag 表在这里固化,后续 ②⑤ 阶段运行时直接读这张表。

4. 记忆口诀

3 句话记住所有挂载点

口诀 1
9 个事件钩子 = 5 个 waterfall(可拦截) + 4 个 emit(只观测)。
waterfall: agent/pre-step / system-prompt/assemble(Layer 1.5)/ agent/request / llm/stream / tools/pre-execute。
emit: session/event / tools/result / tools/change / skills/change。
口诀 2
真正"拦"下来的有 3 道:input-guard 在 pre-step + realm-skill-bridge 在 system-prompt/assemble(Layer 1.5) + tools/pre-execute(Layer 3)。
其他 hook 要么是观测(emit)、要么是改写不拦(waterfall 但放行)。
🚫 REJECT 标签机制:input-guard 拒收 → 写 agent._edgeRejection(小抄)→ throw → dsh-agent-loop 把 reason 翻译丢 → emit turn/end { kind: 'blocked' } → http-api 在 session/event 读小抄转 4xx。reason 在中间丢失,靠小抄传过去。
口诀 3
13 个 service provider + 3 个 LLM/web provider = 不挂 dsh 流程,只挂注册表。
它们在别人的瀑布流里被 softInject 取出来调,自己不订阅事件。
